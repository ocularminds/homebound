# FL-032 - Presence tenant connection missing; web escalation lifecycle implemented

- **Date:** 2026-10-07
- **Component:** Decionis managed Presence, AgentSafe 0.2.5, Alexa web simulator
- **Expected:** A child disarm request opens the parent's native Presence ceremony, then the same saved intent resumes through AgentSafe after fresh Decionis authorization.
- **Observed:** The live request returns `AUTHORITY_UNAVAILABLE` without a handoff. Instrumenting the official SDK's guarded authority transport identifies HTTP 503 with `PRESENCE_TENANT_CONNECTION_NOT_CONFIGURED`. The response is an `error`/`message` envelope, so AgentSafe's expected authority-decision parser reduces it to `AUTHORITY_REQUEST_FAILED`.
- **Impact:** The parent has no approval request to complete. No native Presence approval or subsequent device execution can be validated until the Decionis tenant has its Presence connection configured. The diagnostic did not dispatch a device; the live web request did not perform the disarm.
- **Implemented locally:** A visible approval card, server-derived status and expiry, session-bound voice/button checks, quiet automatic checks, one spoken terminal update, and continued microphone capture during checks. Parent-approval claims only trigger a saved-handoff lookup. Repeated requests do not open duplicate approvals for the same device. Cancellation pauses checking without claiming to revoke Presence approval.
- **Reliability fixes:** Temporary authority failures preserve durable handoffs instead of closing them as denied. Concurrent resumes are serialized within the MCP process. The displayed deadline cannot outlive the captured intent. Lost responses and unknown dispatch stop automatic checking and require review; an uncertain result cannot be reported as not performed.
- **Validation:** 140 Python tests and 10 voice tests pass. A labelled browser fixture verified pending checks, automatic completion, spoken notification, microphone reuse, and expiry presentation. During sampled approval checks, capture remained active and the conversation retained only the original request and terminal update. The 475 × 763 approval screen fits without overflow. These fixture checks do not claim real Presence approval.
- **Required external setup:** Configure the existing Decionis tenant's Presence connection, then verify that its trusted parent is enrolled with the `APPROVER` role. Connection credentials remain in the managed Decionis integration. HomeBound continues using the official managed handoff; no direct Presence calls or invented approval links.
- **Live dialogue check:** Explicit schema enums prevent the model returning a relative's name as a speaker label. “Mum approved the alarm. Can you check the approval?” passed through the real Bedrock interpreter and returned the missing-saved-request response with zero device calls and no change to speaker context. Approval checks ignore unrelated model-extracted conversation facts.
- **Status:** Local escalation lifecycle implemented. FL-029's generic failure is diagnosed; a real parent ceremony is still pending the tenant connection.
